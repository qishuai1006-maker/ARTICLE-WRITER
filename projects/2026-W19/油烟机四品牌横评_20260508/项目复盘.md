## 问题回顾（本次 5 个流程痛点）

### 痛点 1：T5 生图走了两轮（matplotlib → NotebookLM）
**现象**：视觉分发师默认用了 matplotlib 脚本生图，CEO 发现后要求用 NotebookLM 重新生成，6 张图全部重做。
**根因**：CLAUDE.md 虽然写了"T5 统一用 NotebookLM"，但放在第五章平台策略中，视觉分发师未读取到。
**影响**：浪费时间约 30 分钟，且 matplotlib 版本图片分辨率低（1920x1080）已不适用。

### 痛点 2：notebooklm CLI 下载路径嵌套
**现象**：`notebooklm download infographic "outputs/T5_封面图.png"` 在项目根目录执行后，图片落入了 `outputs/outputs/T5_封面图.png`，导致 docx 首次生成时图片缺失，生成了 43KB 的空壳文档。
**根因**：notebooklm CLI 内部在创建父目录时可能误解了相对路径，而 Agent 执行时没有检查 cd 的当前目录。
**影响**：docx 需要重新生成（额外一轮），且排查花了时间。

### 痛点 3：debug 截图和临时脚本未清理
**现象**：17 张 debug_*.png 截图 + 3 个临时脚本（nlm_auto.py, nlm_one_notebook.py, generate_t5_images.py）留在 outputs/，归档时才发现。
**根因**：没有"调试完成后清理"的流程规范，也没有自动检测机制。
**影响**：outputs/ 混乱，归档前需要手动清理。

### 痛点 4：下载后无自动验证步骤
**现象**：NotebookLM 生成完成后下载到本地，用户反馈"图片好像没替换"，需要人工确认文件确实更新了。
**根因**：没有下载后的验证步骤（文件大小/分辨率/修改时间检查）。
**影响**：用户产生不信任感，需要额外沟通确认。

### 痛点 5：notebooklm 命令每次都要手动批准
**现象**：settings.json 的 Bash allow list 中没有 `notebooklm*`，每个 notebooklm 命令（create/list/generate/download）都需要用户点击批准。
**根因**：v6.1 配置时 notebooklm CLI 尚未集成到工作流中，权限列表未更新。
**影响**：用户需要频繁点击批准，打断工作流。

## 经验教训

1. **NotebookLM infographic 质量远超 matplotlib**：同样数据，NotebookLM 生成的信息图在视觉层次、色彩搭配、信息组织上明显更好。后续选购横评型项目优先用 NotebookLM 生图
2. **下载路径要注意 notebooklm CLI 的相对路径行为**：第二次下载时图片落入了 `outputs/outputs/` 嵌套目录，导致 docx 首次生成时图片缺失。教训：下载前先 cd 到项目根目录，或使用绝对路径
3. **debug 截图要及时清理**：17 张 debug 截图 + 3 个临时脚本散落在 outputs，归档时才发现。教训：调试完成后立即清理
